## Needs a decision (not auto-fixed)

### R-1 — Synchronous fsync SQLite commits on the bell path — MED
`session.py` `transition()` → `_persist()` runs inline `sqlite3` commits with `PRAGMA synchronous=FULL` (`persistence.py`), two per bell press, on the same event loop that drives ESP32 feedback and `/ws`. Under SSD write pressure each fsync can stall the loop tens of ms, delaying the local acknowledgment. It is local disk (not a NUC/NAS/cloud call, so not a hard invariant violation), but it is a blocking call on the real-time path. **Recommendation:** offload persistence to a thread executor, or relax to `synchronous=NORMAL` under WAL, and validate button→feedback latency on-device. Needs a latency measurement first — hence not a blind change.

### S-1 — `/ws` is unauthenticated and broadcasts resident identity — MED (by-design for trusted-LAN)
`app.py` accepts every `/ws` connection; the snapshot + `vision.identity_stable` deltas carry `person_id`/`display_name`. Any device on the LAN can subscribe and harvest enrolled residents' names. This is within the documented "trusted kiosk on trusted LAN" model, but there is no app-layer guard if the port is ever exposed.

### S-2 — MQTT bridge widens `/ws` to resident presence/location — MED
The bridge (which I added) re-broadcasts `status.presence_changed` (subject + home/away + geofence/calendar source) onto the same unauthenticated `/ws`. Presence is more sensitive than the ambient tiles the bridge was justified by. **Recommendation:** decide whether presence should reach the wallboard `/ws` at all; if yes, pair with S-1 (authenticate `/ws`) — do not silently narrow the bridge topic filter, as the presence tile depends on it.

### S-3 — Enrollment key + token traverse the LAN in plaintext HTTP — MED (deploy)
Already noted in the encrypted-storage runbook: the Pi fetches the LUKS passphrase over `http://…:8090`. A LAN sniffer/MITM captures both the key and the replayable token, defeating at-rest encryption for an on-network attacker. Outside Option C's powered-off-theft model, but **recommend** fronting the control-plane with TLS (`infra/caddy`). The endpoint is also un-rate-limited (mitigated by `compare_digest` + token entropy).

### S-4…S-6 — lower-severity boundary notes
- Visitor token is placed in `/visitor?token=…` query strings → leaks via access logs / history / `Referer` (bounded: HMAC-signed, session-bound, 300s TTL).
- Public social READ endpoints + visitor-token issuance are un-rate-limited (enumeration/DoS surface only).
- Per-IP limiter uses `request.client.host` with no trusted `X-Forwarded-For`, so it collapses behind a reverse proxy (only the per-session axis remains).
- One shared admin token gates all owner surfaces (documented stopgap pending `packages/auth`).

### Privacy defense-in-depth (low, follow-on)
- **A F-3 (re-evaluated → not a bug; documented instead):** `unenroll` enqueues the remote purge *before* the local delete. On closer review this ordering is **intentional and correct** and must NOT be reordered: the purge outbox is a crash-safe, retrying queue, so enqueue-first is a write-ahead intent — a crash between the two still guarantees the remote archive is eventually purged. Delete-then-enqueue would risk a crash after the local delete but before the intent is recorded → a *permanent remote leak* (the dangerous direction for a deletion invariant). Added a code comment in `service.py` to prevent a future well-meaning reorder.
- **A F-4:** the E-3 redaction filter is installed per-logger; a bare `logging.getLogger("door_visiond.x")` that bypasses `get_logger` would not be filtered. Holds today by discipline; a handler-level filter would make it tree-wide.
